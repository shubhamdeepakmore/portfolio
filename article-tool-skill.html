The Tool Isn't the Skill

Why knowing Power BI matters less than knowing what question to ask.

Most PMO job descriptions read like a tool inventory. Power BI, MS Project, Primavera, Jira, Smartsheet, Excel, Power Automate, SharePoint, Power Query. Sometimes Power Apps for good measure. The candidate who knows the most tools wins, presumably.

I've spent the last few years actually doing PMO work, and I think this framing is mostly wrong. Not entirely wrong — tools matter — but wrong in emphasis. The harder, more valuable skill is the one almost no job description asks about: knowing what question the tool is trying to answer.

The "Power BI expert" problem

I know Power BI reasonably well. I've built dashboards that get used daily. But if you put me next to someone who's been certified to the hilt and knows every DAX function in the book, they will out-Power-BI me on every technical measure.

What I've noticed, though, is that the dashboards that actually get used aren't built by the most technical people. They're built by the people who spent the most time understanding what the user needed before opening Power BI.

The technical bit is genuinely the easier half. The harder half is everything before and after:

- Who is this dashboard for? - What decision are they trying to make with it? - What's the smallest set of numbers that helps them make it? - What happens if the underlying data is wrong — do they know? Can they tell? - Will they actually open this dashboard, or is it going to sit in a folder unused?

None of those questions are answered in a Power BI tutorial. They're answered by sitting with the user, asking what their morning looks like, and figuring out where the friction is.

Tools are interchangeable. Questions aren't.

A few years ago, the dominant PMO tool was Microsoft Project. Before that, Primavera. Power BI displaced Tableau in many shops. Smartsheet is now displacing both Excel and basic project trackers in others. Power Automate is starting to absorb work that used to live in macros.

The tools rotate every few years. The question — what does this team need to see, and how often — doesn't.

If you anchor your professional identity to a specific tool, you have to relearn yourself every five years. If you anchor it to a way of asking questions, the tools become details. You can pick up a new tool in a few weeks if the underlying question hasn't changed.

Why this matters for hiring

Job descriptions optimise for tool keywords because tools are easy to filter on. Atomic, verifiable, binary — either you've used Power BI or you haven't.

But anyone who's worked in a PMO long enough knows the gap between "I've used Power BI" and "I've built something with Power BI that actually changed how the team works" is enormous. The first is a line on a CV. The second is a story about how you figured out what mattered.

When I look at someone's experience, I'm less interested in the tool list than in two questions: have they built something that got used? And can they explain why someone used it?

If they can, the tool was incidental. If they can't, the tool didn't save them.

What I try to do differently

I try to lead with the question, not the tool. When someone asks me to "build a Power BI dashboard", my first response is usually a set of questions about who, why, and how often. Not because I'm being awkward, but because the dashboard hasn't been designed yet — only the request has.

That instinct slows things down at the start and speeds everything up after. It also means that when the tool changes — and it always changes — I don't have to start over. The dashboard might move from Power BI to Smartsheet to whatever comes next, but the underlying question stays the same.

The skill isn't the tool. The skill is knowing what the tool is for.
